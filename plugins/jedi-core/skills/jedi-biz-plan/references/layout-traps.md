# 어떻게 만들까 — 레이아웃 함정과 조립 패턴

> 이 문서는 **문서를 실제로 조립할 때** 걸리는 것들이다. 무엇을 쓸까는 `writing-rules.md`에 있다.
> 전부 실측에서 나온 것이고 추측은 넣지 않았다. 근거는 `PROVENANCE.md`.
>
> ⚠️ **적용 범위** — 실측 환경은 **Windows + 한컴오피스 + Word COM + python-docx**이고
> 표본은 문서 3건이다. 아래 수치(줄간격 `line=259`, 픽셀 환산값 등)는 **그 양식에서 잰 값**이라
> 다른 양식에서는 다시 재야 한다. 🔑 **값이 아니라 재는 방법을 가져다 쓸 것.**

## 1. 🔴 분량은 문장으로만 줄어든다

14페이지를 줄이려고 시도한 것과 결과다.

| 시도 | 결과 |
|---|---|
| 캡처를 **글자가 뭉갤 때까지** 축소 (4.6in → 2.4in) | 13p 그대로 |
| 다시 원래 크기로 복원 | **13p 그대로** |
| 줄간격 1.08 → 1.00 | 변화 없음 |
| 문단 뒤 간격 3.5pt → 2pt | 변화 없음 |
| `keep_together` 제거 | 오히려 여백 증가 |
| `keep_with_next` 제거 | 변화 없음 |
| **문장 1,000자 삭제** | **14p → 13p** ✅ |

🔑 **지면은 텍스트가 지배한다.** 그림·여백·간격을 만지는 것은 품질만 깎고 페이지는 안 준다.

표·그림으로 압축하려면 글을 실제로 덜어내고 그 내용을 표가 대신 지게 만들어야 한다. 문장을 남긴 채 표를 더하면 늘기만 한다.

### 줄간격 레버는 조건부다

「분량이 넘칠 때 줄 간격(0.9~0.95)이 가장 안전한 레버」라는 통념이 있는데 **양식에 따라 안 듣는다.** 위 사례의 양식은 이미 `line=259`(1.08배)로 최소치에 가까웠다.

**먼저 현재 값을 재고, 여유가 있을 때만 레버로 쓴다.**

```python
# docDefaults의 현재 줄간격 확인 (240 = 1.0배)
re.search(r'<w:spacing[^/]*w:line="(\d+)"', styles_xml)
```

### ⚠️ `trHeight` 제거는 규정 위반 소지가 있다

정부 양식은 본문 셀에 `trHeight`(최소 높이)가 걸려 있어 내용이 짧아도 페이지를 통째로 먹는 경우가 있다. 제거하면 실제 분량대로 렌더링되지만, 양식에 **「항목 및 서식 임의 수정 불가」**가 명시돼 있으면 건드리지 않는 편이 안전하다. 문장으로 해결한다.

## 2. 🔴 이미지는 1×1 표에 넣는다

그림과 캡션을 **테두리 없는 1×1 표**에 담고 행에 `cantSplit`을 건다. 둘이 한 표에 묶여 페이지를 넘겨도 갈라지지 않고, 위치와 폭 관리도 쉽다.

🔑 **이 표는 「한 페이지에 이미지와 표를 함께 두지 않는다」(`writing-rules.md` §5)에 걸리지 않는다.** 그 규칙이 막는 것은 심사자가 두 번 판단하게 만드는 **내용 표**이고, 이쪽은 테두리도 없어 렌더링 결과에 표로 보이지 않는다.

```python
t = host_cell.add_table(rows=1, cols=1)
c = t.rows[0].cells[0]
c.paragraphs[0].add_run().add_picture(path, width=Inches(w))
cp = c.add_paragraph(); cp.add_run(caption).font.size = Pt(9)
# tblBorders 전부 none + 각 행 trPr에 <w:cantSplit/>
```

⚠️ **「한 문단(add_break) + keep_together」 방식은 폐기됐다.** 캡션은 붙었지만 `keep_with_next`가 다음 문단까지 끌고 가 페이지 하단 2~3인치를 통째로 버렸다. 표 방식에는 이 문제가 없다.

⚠️ **기존 문서에서 그림을 꺼내 재사용할 땐 캡션 중복을 주의한다.** 그림 문단이 캡션을 이미 품고 있으면(그림 run → break → 캡션 run) 표로 감싸며 또 넣어 두 번 찍힌다.

## 3. 🔴 캡처와 도식은 축소 내성이 다르다

**직접 만든 도식**은 인치 좌표계로 폰트를 역산해 넣으므로 2.3인치로 줄여도 7.5pt로 읽힌다.
**화면 캡처**는 원본 글자 크기가 고정이라 같은 비율로 줄이면 판독이 불가능해진다.

- 지면이 모자라면 **도식부터** 줄이고 캡처는 마지막에 손댄다
- 🔴 **판독 안 되는 캡처는 지면만 먹는다.** 증거로 넣은 것이 증거 구실을 못 하면 빼는 편이 낫다

삽입 폭은 문서에서 보이는 pt로 역산해 정한다. 하한 6pt, 본문 15pt 기준으로 7pt 이상을 권장한다.

```
보이는 pt = 원본 캔버스 fontsize × (삽입 폭 ÷ 원본 캔버스 폭)
```

**캡처 원본 해상도 공식** — 원본 글자 42px(device_scale 3, 14px 폰트)가 문서에서 6pt로 보이려면 `이미지 폭 ≤ 42 × 425pt / 6pt ≈ 2,975px`. 좌우 2단으로 합치면 폭이 두 배가 되어 글자가 절반이 되고 **2.8pt로 읽을 수 없게 된다**(실제 사고).

## 4. 도식 제작 — 좌표계를 인치로 고정한다

```python
W = 5.9                      # 삽입 폭과 동일하게
fig, ax = plt.subplots(figsize=(W, H))
ax.set_xlim(0, W); ax.set_ylim(0, H)
fig.subplots_adjust(left=0, right=1, top=1, bottom=0)
```

- 임의 좌표계(0~100)를 쓰면 박스 높이 대비 폰트가 넘쳐 **글자가 박스를 뚫는다**(실제 사고)
- 삽입 폭에 1:1로 그리면 fontsize 값이 문서에서 보이는 pt와 같아진다 → 본문 15pt 기준 12~14pt가 적정
- 박스 간격은 0.35인치 이상. 좁으면 화살표 라벨이 박스에 겹친다
- 설명 문구는 한 줄로 줄여 공간을 벌고 폰트를 키운다
- 🔴 **한 줄에 여러 정보를 몰아넣지 않는다** — 태그·숫자·설명을 한 줄에 배치했다가 글자가 겹쳤다. 설명은 박스 밖 열로 뺀다
- **만든 그림은 반드시 눈으로 본다.** 코드가 정상 종료해도 글자는 겹친다

## 5. 라이브 서비스 캡처 (Playwright)

- **`element.screenshot()`을 쓴다.** `bounding_box()`는 뷰포트 좌표인데 `full_page` clip은 문서 좌표라 **스크롤만큼 어긋난다**
- 대상 요소에 JS로 id를 부여한 뒤 `locator('#id').screenshot()` — 텍스트 매칭보다 확실하다
- **sticky 헤더는 캡처 직전에 숨긴다.** 단 챗봇 입력란도 sticky일 수 있으니 **대화 완료 후에** 숨긴다
- 챗봇은 실제로 문장을 보내 응답을 받은 상태로 찍어야 "AI가 알아듣는다"가 보인다
- 이미지 생성 AI는 **한글이 깨져 부적합하다.** HTML 렌더링이 픽셀 정확하다

## 6. docx 실무 함정

### 🔴 페이지 수는 글자수로 추정할 수 없다

189자를 넣었더니 1페이지가 늘었는데, 이후 119자를 지웠을 땐 0페이지였다. 페이지 경계 효과 때문이다. 추정 8p가 실제 14p였던 사례도 있다.

**Word COM `Repaginate()` + `ComputeStatistics(2)` 실측만 신뢰한다.**

### 🔴 `cell.text`는 중첩 표 내용을 제외한다

문항이 큰 표의 셀 안에 있고 그 안에 표가 또 있는 구조에서, 문항 글자수를 `cell.text`로 세면 절반도 안 잡힌다(실측: 811자로 나왔으나 실제 1,265자).

**「각 문항 1,000자 이상」 게이트는 반드시 중첩 표 포함으로 센다.**

### 🔴 중첩 표는 헤더 반복이 안 된다

Word 자체가 중첩 표의 헤더 행 반복(`tblHeader`)을 지원하지 않는다. 게다가 python-docx로 `trPr`에 `append`하면 **스키마 자식 순서 규칙**(cantSplit → trHeight → tblHeader)을 어겨 **조용히 무시**된다. 로그가 「적용됨」이라 떠도 렌더링 전엔 믿지 않는다.

표가 페이지에 걸치는 것을 막으려면 표 전체를 다음 장으로 밀어야 하는데, 분량 규정과 충돌하면 규정을 택하는 편이 낫다.

### 🔴 레이아웃 결함은 렌더링해야만 보인다

텍스트만 읽으면 절대 안 보이는 것들이다. 페이지 첫 줄이 「다.」 한 글자 / 단어가 「지」+「역으로」로 갈림 / 마지막 장에 두 줄만 남아 1페이지 낭비.

**전 페이지를 PNG로 렌더링해 한 장의 컨택트 시트로 합성**하면 빈 페이지·잘린 표·글자 넘김이 한눈에 잡힌다. docx → PDF는 Word COM, PDF → PNG는 PyMuPDF.

### 폰트·간격 실측 값

| 항목 | 값 |
|---|---|
| 본문 폰트 | 양식이 지정한 크기 그대로 (예: 맑은고딕 15pt) |
| **표 내부 폰트** | 본문보다 3~4pt 작게 (11~12pt) — 그러지 않으면 4열 표가 페이지를 다 먹는다 |
| 줄간격 | 1.0~1.15 (대부분 양식이 "줄간격은 일부 조정 가능"을 허용) |
| 헤드라인 | 본문보다 1pt 작게 + 굵게 + 점선 테두리 |
| 이미지 캡션 | 11pt, 가운데, 기능·상태만 |

## 7. hwp 원본에서 표를 가져올 때

일반 hwp 파서는 **표 셀 내용을 대부분 유실한다**(제목·구조만 나온다). 정확히 뽑으려면:

1. 한컴오피스 COM으로 `.hwpx`로 변환 → `Contents/section0.xml`을 XML 파싱 (`hp:tbl` → `hp:tr` → `hp:tc`)
2. 시각 서식(음영·테두리·정렬)은 PDF로 변환 후 페이지를 이미지로 렌더링해 눈으로 확인

이 두 단계를 거치면 원본 표가 셀 단위로 복원된다(실측: 표 31개 100%).

## 8. 🔴 값을 바꾼 뒤에는 「바뀌었는지」를 읽어서 확인한다

표지 날짜 치환이 **한 번도 성공한 적이 없는데 로그에는 계속 「바뀌었다」로 찍혔다.** `print`가 성공 여부와 무관한 자리에 있었기 때문이다.

원인은 run이 `'2'` / `'026. '` / `'0'` / `'.'` 넷으로 쪼개져 있어 `'0.'`을 찾는 조건이 애초에 맞지 않은 것이었다. 한글·docx의 텍스트는 **한 문장이 여러 run으로 쪼개져 있는 것이 기본**이라, 문자열 매칭은 자주 빗나간다.

```python
# 나쁨 — 치환 시도와 성공 보고가 분리돼 있다
replace(para, '0.', new); print('날짜 교체 완료')

# 좋음 — 바꾼 뒤 다시 읽어 값으로 판정한다
replace_all_runs(para, old, new)
after = ''.join(r.text for r in para.runs)
assert new in after, f'치환 실패: {after!r}'
print(f'날짜 = {after}')
```

## 9. 조립 순서 (권장)

1. 양식 원문에서 **작성요령·폰트·페이지 상한**을 읽는다 (추측 금지)
2. 문항별로 글을 먼저 완성한다 — 이때 그림 자리는 마커만 둔다
3. 표를 넣으면서 **같은 내용의 문장을 삭제**한다 (§1 치환 원칙)
4. 그림을 1×1 표로 삽입한다 (§2)
5. PDF → PNG 컨택트 시트로 눈으로 본다 (§6)
6. 넘치면 **문장을 덜어낸다** (§1)
7. 표지 빈칸을 채우고 **읽어서 확인한다** (§8)
