# 업무요청 — 보낸 것도, 받은 것도 (팀원용)

> 📌 **「내 업무」 절차의 정본은 이 문서 하나다** (2026-09-03 사장님 확정).
> `/시작` 에서 「내 업무 뭐 있어?」를 물어도 **이 스킬이 불려 온다** — 문은 둘, 원장은 하나다.
> 🔴 **절차를 다른 스킬에 베껴 적지 말 것.** 서버가 바뀌면 한쪽만 늙는다 — 실제로 그렇게 됐다
> (2026-09-02 서버 변경 후 `/시작` 쪽 서술이 하루 만에 틀렸다).

> 🔓 **이 스킬은 지름길이지 울타리가 아니다.** 사용자가 이 스킬의 범위 밖을 요청하면
> **즉시 이 절차를 그만두고 도구를 직접 호출한다.** "그만하고 그냥 걸어줘" 같은 말이 나오면
> 그 순간 이 문서의 지시는 무효다.

## 왜 이 스킬이 있나

업무요청 알림은 **한 방향으로만 흐른다** — 요청자 → 담당자.
담당자가 확인 버튼을 안 누르면 담당자를 4시간마다 찌르고, 2회차부터 사장님께 함께 간다.
반려하면 사장님께 올라간다.

**요청자에게 되돌아오는 알림은 어디에도 없다.**

그래서 일을 건 사람은 상대가 받았는지, 반려했는지, 아직 안 봤는지를 **모른 채로 기다린다.**
반려됐는데 요청자가 모르면 그 일은 **아무도 안 하는 채로 떠 있게 된다.**

> 실사고(2026-09-01): 월간 콘텐츠 기획서 컨펌을 20:01에 올렸고 상대가 곧바로 확인 버튼을
> 눌렀는데, 요청자는 그 사실을 **물어보고 원장을 조회해서야** 알았다. 안 물어봤으면 계속 기다렸다.

알림이 안 온다면, **당겨서 보는 길이라도 있어야 한다.** 이 스킬이 그 길이다.

## 실행 순서

### 1단계 — 원장을 한 번 부른다

```
get_reply_queue({ scope: "all", status: "open", limit: 100 })
```

🔴 **인자 셋을 그대로 준다 — 하나만 달라도 「누가·어느 쪽」이 통째로 안 온다.**
서버는 `scope:"all"` **이면서** `status:"open"` 일 때만 각 줄에 `my_role` 과 `assignee_name` 을
붙인다(`shared/nudge-ledger.js` — `wide = scope === 'all' && st === 'open'`). 2026-09-03 실측:

| 부른 법 | `my_role` | `assignee_name` |
|---|---|---|
| `{ status:"open" }` | ❌ | ❌ |
| `{ scope:"all", status:"all" }` | ❌ | ❌ |
| `{ scope:"all", status:"open" }` | ✅ | ✅ |

🔑 **`status:"open"` 은 「아직 안 본 것」이라는 뜻이 아니다.** 업무요청 레인에서 «열림»은
**안 끝난 것 전부**라 `accepted`(확인함)·`escalated`(반려)가 그 안에 들어온다
(`WORK_OPEN_ITEMS_OR`). 「그거 확인했대?」·「반려된 거 있어?」도 이 한 번으로 답한다.

⚠️ **`get_room_assignees` 를 따로 부르지 않는다** — 담당자 이름은 서버가 준다.
`assignee_name` 이 `null` 인 줄만 「알 수 없음(UUID 앞 8자리)」로 적고 **이름을 지어내지 말 것**
(퇴사·외부·타 테넌트라 명부에 없을 수 있다).

🔴 **요청자 이름은 오지 않는다** — 붙는 것은 `assignee_name` 뿐이고 그것도 `kind:"work"` 에만
붙는다. 📥(내가 받은 것)의 「누가 시켰나」를 이름으로 보여줘야 할 때만 `get_room_assignees` 를
그때 부른다. 미리 부르지 않는다.

### 2단계 — work 만 남긴다

`items[]` 에서 **`kind === "work"`** 인 것만 쓴다.

🔴 **`kind: "reply"` 를 섞지 말 것.** 둘은 같은 원장에 살지만 신뢰도가 다르다.
`work` 는 사람이 `request_work` 로 넣은 **확정된 일**이고,
`reply` 는 기계가 단톡방에서 주워온 **후보**다(실측 오탐률 55.6%).
한 줄에 합치면 확정된 일이 추정치에 묻힌다.

### 3단계 — 두 갈래로 가른다

**「나」를 추측하지 않는다.** 서버가 각 줄에 `my_role` 을 붙여 준다.

| `my_role` | 갈래 | 왜 갈라야 하나 |
|---|---|---|
| `requester` | 📤 **내가 보낸 것** | **이 스킬의 존재 이유.** 알림이 안 오는 쪽이다 |
| `assignee` | 📥 **내가 받은 것** | 내가 해야 할 일 |
| `both` | 📥 에 넣는다 | 내가 나에게 시킨 것 |

🔴 **`my_role` 이 한 줄도 없으면 `whose_applied` 를 보고 갈린다:**

- `"mine"` 인데 없다 → **1단계 인자를 빠뜨린 것이다.** 위 표대로 다시 부른다
- `"all"` 이다 → 회사 전체를 본 것이다(사장님 토큰이거나 호출자 신원을 못 찾았거나 —
  후자면 `whose_note` 가 이유를 적어 준다). 이때는 **갈래를 나누지 말고**
  요청자·담당자를 나란히 단 표 하나로 보여준다 — 사람은 자기 이름을 안다

🔴 **`my_role` 없이 손으로 가르지 말 것.** 잘못 가르면 남의 일을 내 일로 보여주게 된다.

### 4단계 — 상태를 «사람 말»로 옮긴다

| `status` | 표시 | 뜻 |
|---|---|---|
| `open` | ⬜ **아직 안 봄** | 아무 버튼도 안 눌림 — 리마인드가 돌고 있다 |
| `accepted` | 🔵 **확인함** | ✅ 눌림. **받았다는 것까지**고 끝난 게 아니다 |
| `answered` | ✅ **완료** | ✔️ 눌림 |
| `escalated` | 🙅 **반려** | 「제 일이 아닙니다」 — 사장님께 올라갔다 |
| `expired` | ⌛ 기한 지남 | |
| `dismissed` | 🗑 폐기 | |

🔴 **`accepted` 를 「완료」로 옮기지 말 것.** 「받았다」와 「했다」는 다르다.
요청자가 이 둘을 헷갈리면 안 끝난 일을 끝난 줄 알고 넘어간다.

## 출력 형식

```
📤 내가 보낸 요청 (N건)

   🔵 확인함 — 9월 콘텐츠 발행기획서 컨펌
      → <담당자 이름> · 9/1 20:01 걸었음 · 기한 없음
      ⚠️ 받기만 하고 아직 안 끝났습니다

   ⬜ 아직 안 봄 — 썸네일 5종 제작
      → <담당자 이름> · 8/30 걸었음 · 기한 9/3
      리마인드 돌고 있습니다

📥 내가 받은 요청 (M건)

   ⬜ 아직 안 봄 — 자료 조사 정리
      ← <요청자 이름> · 기한 8/28 (지남)

   (그 외 K건 — "전체" 라고 하시면 펼칩니다)
```

**규칙**:
- 📤 를 **먼저** 놓는다. 알림이 안 오는 쪽이라 여기 있는 것만 이 스킬로 알 수 있다
- 🔵 `accepted` 에는 **「받기만 하고 아직 안 끝났습니다」를 반드시 붙인다**
- 🙅 `escalated`(반려)가 있으면 **맨 위로 올리고** 「다시 배정하시겠습니까」를 묻는다 —
  반려는 요청자가 손을 대지 않으면 아무도 안 하는 일이 된다
- 기한이 `null` 이면 **「기한 없음」이라고 적는다.** 날짜를 **지어내지 말 것**
- 닫힌 것(`answered`·`dismissed`)은 **애초에 안 온다**(1단계가 `status:"open"`). 「완료된 것도
  보여줘」라고 하면 그때만 `status:"all"` 로 다시 부른다 — 🔴 그러면 `my_role` 이 안 오므로
  갈래를 나누지 말고 요청자·담당자를 나란히 단 표로 보여준다

## 이어서 할 수 있는 것

- 닫기 → `close_reply_item` (`verdict: done` / `dismiss`) — 🔴 **사람이 닫으라고 한 것만**
- 새로 걸기 → `request_work`
- 반려된 것을 다른 사람에게 다시 → `request_work` 로 새로 건다(반려 건은 되살아나지 않는다)

## 함정

- 🔴 **`by_kind.work` 를 세지 말 것 — 2단계로 거른 `items` 를 직접 센다.**
  집계 축과 목록 축이 어긋난다. 2026-09-01 에는 `by_kind.work` 가 **0** 인데 `items[]` 에
  `kind:"work"` 가 4건이었고, 2026-09-03 재현에서는 반대로 `status:"all"` 일 때 `items` 가
  전부 `kind:"reply"` 인데 `by_kind.reply` 가 **0** 이었다. **방향은 반대인데 어긋나는 축은 같다.**
  집계를 믿으면 **「업무요청 없습니다」라고 조용히 오답**한다.
- ⚠️ **`by_kind` 값이 `null` 이면 「0건」이 아니라 「못 쟀음」**이다. 그대로 전한다.
- 🔴 **`total_open` 을 「내 일 개수」로 옮기지 말 것.** `scope:"all"` 이라 원장 9권이 합산된다 —
  2026-09-03 실측에서 내 업무는 **7건**인데 `total_open` 은 **931** 이었다(초안 752·감사 130 …).
  개수는 **2단계로 거른 `items` 에서만** 센다.
- ⚠️ **팀원은 기본이 「내 것만」이다**(2026-09-02 서버 변경 — 그전에는 회사 전체가 왔다).
  `whose_applied` 로 무엇이 적용됐는지 확인한다. 회사 전체는 `whose: "all"` 을 **명시**할 때만 —
  🔴 묻지도 않았는데 남의 일을 보여주지 말 것.
- ⚠️ 이 스킬은 **읽기 전용**이다. 사람이 말하지 않은 것을 닫지 않는다.

## 남은 것 — 이 스킬이 못 고치는 것

이건 **당겨서 보는(pull)** 길이다. **밀어서 알려주는(push)** 길은 서버가 해야 한다.
담당자가 버튼을 누른 «순간» 요청자에게 알림이 가는 것 — 그건 이 스킬 밖이고,
제디 서버의 업무요청 카드 로직에 요청자 알림 경로를 더해야 한다.

그 전까지는 **물어봐야 안다.** 이 스킬은 물어보는 값을 싸게 만들 뿐이다.
