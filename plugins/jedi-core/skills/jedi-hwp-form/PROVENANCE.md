## 어디서 나온 것인가

2026-08-08 협회 제출용 신청서(6쪽, 표 65칸·사진·도장) + 동의서(1쪽, 도장)를
공양식에서 스크래치로 작성하며 얻은 처방이다. 한 세션에서 **8번 재빌드**했고
그 중 4번은 진단이 틀려서였다. 함정 9종은 전부 그 과정에서 하나씩 드러난 것이다.

최종 산출물은 기존 방식(한글 COM 직접 조작)으로 만든 완성본과 대조해 검수했다:

| 항목 | COM 방식 | 이 방식 |
|---|---|---|
| 쪽수 | 6 | 6 |
| 그림 3개 크기·위치 | — | 전부 일치 (0.4mm 이내) |
| 본문 2~6쪽 글자 | 3,892자 | **3,892자 · 공백무시 동일** |
| 여백 | 좌10.0 상9.3 우끝183.7 | 동일 |
| 동의서 | 1쪽 / 491자 | **1쪽 / 491자 · 완전 일치** |

## 핵심 수치

- `1mm = 283.46 HWPUNIT` — 도장 `4275` 를 15.08mm 로 역산해 검증
- 그림 표시 크기 = **이미지 픽셀 / 96dpi** — 152px 도장에 15.1mm 를 지정했으나
  40.3mm 로 그려졌고 `152 / 96 * 25.4 = 40.2mm` 와 일치
- 줄배치를 비우면 재계산 — 179자가 1줄 → **24줄**로 접힘

작업 중 뜨는 창이 두 가지다. 성격이 완전히 다르다.

|---|---|---|
| 동의서 | ✅ 460자, 치환 반영 | ❌ `Open=False`, 본문 0자 |
| 신청서 양식 | — | ❌ `Open=False`, 본문 0자 |
| 같은 라이브러리의 `.hwpx` 경로 | — | ✅ 2쪽 / 1,137자 |

자기 검증은 통과하는데 **진짜 소비자(한글)가 거부**하는 형태다. `.hwpx`(zip 재작성)만
작동하므로 편집은 반드시 그 경로로 한다.

## `hwp-mcp` 와의 역할 분담

같은 파일을 다루지만 겹치지 않는다.

| 단계 | 담당 | 이유 |
|---|---|---|
| `.hwp` 읽기·표·그림 목록 | **`hwp-mcp`** | 한컴 없이 읽는다. 이 스킬에 없는 능력 |
| `.hwpx` 편집 | **`hwpx_lib`** | `hwp-mcp` 의 쓰기는 `content.replace()` 한 줄이라 함정 9종이 안 걸러진다 |
| 변환·검수 | **`hwpform.py`** | 한컴 COM + PDF 대조 |

`hwp-mcp` 는 `jedi-core/.mcp.json` 에 이미 등록돼 있어 별도 배선이 필요 없다.

## 검증 안 된 것 (약속하지 않는다)

- **백지에서 새 문서 만들기** — 서식 정의(글꼴·문단·테두리)를 통째로 지어내야 한다.
  근거가 없으므로 이 스킬의 범위에서 뺐다.
- **표 구조 자체를 바꾸기** (행 추가·칸 병합) — 값 채우기만 검증했다.
- **`.hwpx` 왕복 무손실** — `.hwp → .hwpx → .hwp` 왕복은 쪽수·그림·글자 일치를
  확인했으나 표본이 1건이다.

## v1.2.0 — 줄배치를 안 비우면 「넘침」이 아니라 파일이 안 열린다 (2026-08-10)

같은 양식(모두의창업 1R 활동보고서)의 **글자를 고치는** 작업에서 나왔다. 함정 ① 은
증상을 *「칸 밖으로 넘침」* 으로만 적고 있었는데 실제로는 더 나빴다.

### 실측 — 문장 하나를 45자 → 75자로 늘리고 저장

| 단계 | 결과 |
|---|---|
| `replace_text` 7건 (전부 기대 건수 1건 일치) | 정상 |
| `check_wellformed(section0=xml)` | **통과** |
| zip 안 XML 20개 전수 `ET.fromstring` | **20/20 정상** |
| zip 구조 (파일 수·mimetype·첫 항목) | 무편집본과 **동일** |
| `to-hwp` 변환 | 🔴 **열기 False / 11쪽 → 3쪽** |

즉 **저장 직전 게이트 어느 것도 이것을 잡지 못한다.** XML 은 유효하고 구조도 같다.

### 원인 분리 — 무편집 대조군 1회

```bash
python scripts/hwpform.py to-hwp "work.hwpx" "ctrl.hwp" "ctrl.pdf"   # 아무것도 안 고친 것
# → 열기 True / 11쪽
```

이 한 번이 「변환 경로 문제」와 「내 편집 문제」를 갈랐다. 대조군이 정상이므로
범인은 편집이고, 실제로 **바꾼 문단 6개의 `linesegarray` 를 비우자 열기 True / 11쪽** 으로 풀렸다.

### 전체 초기화는 쓰지 않았다

`clear_lineseg_text_paras(xml)` 는 글자 있는 문단 **전부**를 비운다. 이 문서는
직전 회차에서 들여쓰기(`intent` 음수)와 그림 위치를 어렵게 맞춰 둔 상태라, 전체에
걸면 그것까지 재계산된다. **바꾼 문단만** 마커로 찾아 비우고 처리 개수를 `assert`
로 고정했다.

### 곁가지 — 목록 한 줄에는 단어를 못 넣을 수 있다 (함정 ⑫)

`③` 항목에 설명 한 마디를 덧붙였더니 그 줄만 두 줄이 되고 둘째 줄이 왼쪽 끝에
붙어 정렬이 깨졌다. 폭을 세어 보니 —

| 줄 | 폭 | 여유 |
|---|---|---|
| ② (최장) | **59** = 한 줄 한계 | 0 |
| ③ (대상) | 57 | **2** |

가장 짧은 후보(`·업체 미팅`)조차 폭 10 이라 **원리적으로 불가능**했다. 「조금만 줄이면
되겠지」로 두 번 시도한 뒤 실측으로 접었고, 설명은 아래 문단으로 내렸다.

### 곁가지 — 문단 「제거」는 `replace_text` 로 안 된다

텍스트를 빈 문자열로 바꾸면 **빈 문단이 남아 여전히 한 줄을 차지**한다. 문단 노드
자체를 들어내야 하고 `hwpx_lib` 에 그 함수는 없다. 앵커 두 개(문단A 끝 ~ 문단C 끝)의
인덱스로 슬라이싱했고, **제거 대상이 정확히 3문단인지 `assert` 로 잠갔다**(표·셀
경계를 넘어 잘라내면 문서가 깨진다). 이 방식으로 자수는 그대로 두고 줄 수만 3줄을
줄여 **빈 쪽 하나를 없앴다**(11쪽 → 10쪽, 본문 자수는 726 → 729자로 오히려 증가).

### 곁가지 — `vertAlign` 은 `<hp:tc>` 가 아니라 `<hp:subList>` 속성

표 칸의 세로 정렬을 바꾸려고 `<hp:tc>` 여는 태그에서 찾다 실패했다. 실제 위치는
그 안의 `<hp:subList ... vertAlign="CENTER">` 다. 참고로 이 양식은 답변 칸 **세 개
모두 CENTER** 라, 내용이 칸을 못 채우면 남는 공간이 위아래로 반씩 나뉜다 — 양식의
성질이지 편집 결함이 아니므로 함부로 바꾸지 말 것(서식 수정 금지 조항이 흔하다).

## 2026-08-13 — 「다 됐다」는 문서를 실물로 다시 보고 나온 것 (함정 ⑬~⑯)

강원 도약창업 제4회 심의위 제출서류를 **완성 상태로 두고** 8종 24쪽을 전부 이미지로
렌더링해 한 장씩 눈으로 봤다. **8건이 나왔다.** 앞선 세션의 검사기는 「0건」이었고,
그 검사기에는 이탤릭 축도 쪽 경계 축도 없었다.

| 무엇 | 실측 |
|---|---|
| 이탤릭 | `italic="1"` **속성** 검색 → **0건**. `<hh:italic/>` **자식 요소** → 4개(charPr 58·60·63·64), 그 서식이 붙은 run **41곳**이 전부 기울어져 있었다 |
| `H.HPF` | `Contents/content.hpf` = **1,730 bytes 매니페스트**. 글자 서식은 `Contents/header.xml`. 매니페스트를 고치고 「저장 완료」가 떴다 |
| 빈 결과 통과 | `assert all(v==1 for v in removed.values())` — `removed` 가 `{}` 라 **`all([])` = True** 로 통과. 이탤릭 제거 0건인 채 다음 단계로 갔다 |
| 셀 높이 | 요청사유 셀 **선언 51.8mm = 실제 51.8mm**(초과 0.0). 줄간격을 160→150% 로 낮춰도 표 높이 **240.3mm 그대로** |
| 여백으로 쪽수 | 가용 252mm < 필요 262mm(제목표 18.5 + 간격 3.2 + 본표 240.3). 상단 15→8, 하단 10→5 로 가용 **264mm** → **2쪽 → 1쪽** |
| `pageBreak` | 34행 표가 `CELL` 이라 쪽 경계에서 셀이 **잘리고**(`AP서버(개발용)` 가 「…자동」/「(개발용) 배포」로 갈림) 병합 라벨이 **2곳 소실**. `TABLE` 로 바꿔 해소 |

### 검수 대조가 실제로 무엇을 말했나

`verify --baseline` 결과를 「일치/불일치」로만 읽으면 안 된다. 세 건 모두 **차이가 설명됐다**:

| 문서 | 결과 | 해석 |
|---|---|---|
| 계약서 | 글자 5,546 → 5,567 (+21) · **공백무시 일치 True** | 서식만 바뀌어 줄바꿈 위치가 이동. 내용 동일 |
| 과업지시서 | 1,452 → 1,442 (−10) · 일치 **False** | 표를 2쪽부터 시작시켜 **1쪽의 표 헤더 한 벌**(`구분`+`요구사항 명`)이 사라진 것. diff 가 정확히 그 문자열을 짚었다 |
| 심의승인요청서 | 「안 채운 자리 1건: `년 월 일`」 | **결함이 아니라 사용자가 비워두기로 한 칸**이었다(제출일 확정 후 기입) |

### 왜 「검사기 0건」이 반복되는가

이 스킬의 검수는 **가진 축으로만** 잰다. 이탤릭·쪽 경계·서체 불일치는 축이 없어서
0건이었지 깨끗해서가 아니었다. **축을 늘리는 것보다 먼저 할 일은 실물을 보는 것**이고,
그래서 4단계 끝에 「한글로 열어 눈으로 확인」이 있다 — 그 문장은 장식이 아니다.
